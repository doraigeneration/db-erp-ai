# אפליקציית הניהול - Kilohertz Admin

## מה זה

Kilohertz Admin היא ממשק הניהול של המערכת: אפליקציית ווב פרטית שנועה אברהמי פותחת בתחילת יום העבודה. היא מרכזת במסך אחד את מה שהתהליכים ב-n8n מייצרים ברקע, ומאפשרת להזין רשומות חדשות בלי להיכנס ל-Airtable.

מה יש בה:

| מסך | תוכן |
|---|---|
| לוח בקרה | הכנסות החודש (סכום Total של חשבוניות בסטטוס Done מהחודש הנוכחי), מספר חשבוניות פתוחות, לידים לפי סטטוס, משימות פתוחות |
| חשבוניות | טבלה עם חיפוש וסינון, תג צבעוני לסטטוס, ועמודת קישור למסמך בדרייב (PdfUrl) |
| לידים | טבלה עם חיפוש וסינון לפי סטטוס |
| מוצרים | קטלוג לקריאה בלבד |
| משימות | טבלה עם סימון משימות שעבר מועדן |
| לקוחות | כרטיסי לקוח מטבלת Customers, לקריאה בלבד (ראו "מסכי לקוחות והזמנות") |
| הזמנות | הזמנות מטבלת Orders עם תג סטטוס, לקריאה בלבד (ראו "מסכי לקוחות והזמנות") |
| טפסים | יצירת ליד, חשבונית ומשימה |
| צ'אט | שיחה עם העוזר של קילוהרץ: ממשק צ'אט שרץ ב-WF13 וקורא נתונים בלבד. הוא תוספת לנוחות ואינו אחד משלושת סוכני המערכת (מנהל, שירות לקוחות, מכירות) |

### מסכי לקוחות והזמנות

רשימת המסכים המינימלית במטלה כוללת לקוחות והזמנות, ולכן שני המסכים הם חלק מהאפיון ונבנים כבר בפרומפט הראשי. הנתונים שלהם מגיעים מהטבלאות המורחבות `Customers` ו-`Orders`, שמוגדרות ב-[`data/schema.json`](../data/schema.json) (`core: false`) ואינן חלק מבסיס הליבה שהתהליכים משתמשים בו.

כדי להפעיל אותם:

1. יוצרים ב-Airtable את הטבלאות `Customers` ו-`Orders` עם השדות שב-schema.json.
2. מרחיבים את הרשימה המותרת ב-WF13. זה שינוי של שורה אחת: בצומת `Route By Action`, בכלל של `list`, מחליפים את `['Invoices', 'Leads', 'Products', 'Tasks']` ב-`['Invoices', 'Leads', 'Products', 'Tasks', 'Customers', 'Orders']`.

עד שזה נעשה, WF13 מחזיר לבקשת `list` על הטבלאות האלה שגיאה (טבלה לא מותרת), והמסכים מציגים מצב ריק בעברית ("הטבלה עדיין לא הופעלה") במקום הודעת שגיאה. כך האפליקציה שלמה כבר מהיום הראשון, והמסכים מתמלאים ברגע שהטבלאות מופעלות, בלי לבנות מחדש את הממשק.

### מה קורה אחרי שליחת טופס

הטפסים לא רק כותבים רשומה. כל כתיבה נכנסת ל-Airtable ומפעילה את התהליכים ב-n8n, בדיוק כמו רשומה שהוזנה בכל דרך אחרת:

| טופס | מה נכתב | מה קורה אחר כך |
|---|---|---|
| חשבונית חדשה | רשומה ב-Invoices עם Status = New, בלי מספר ובלי מע"מ | תוך כדקה WF01 מחשב מע"מ וסה"כ ומעביר ל-Pending (או ל-Invalid עם הסיבה ב-Notes). בדקה שאחריה WF08 נותן מספר רץ, מפיק מסמך HTML, שומר בדרייב, כותב את הקישור ב-PdfUrl ומעביר ל-Done |
| ליד חדש | רשומה ב-Leads עם Status = New | WF13 בודק קודם אם המייל כבר קיים, כמו WF03. אם כן, מוחזר HTTP 409 ולא נוצרת רשומה, והטופס מציג "ליד עם המייל הזה כבר קיים". ליד חדש ייכנס לתור של סוכן המכירות (WF04a) |
| משימה חדשה | רשומה ב-Tasks עם Status = Open | המשימה זמינה מיד לסוכן המנהל בטלגרם ולעוזר הצ'אט באפליקציה |

האפליקציה נבנית בתיאור בשפה חופשית ב-Lovable או ב-Base44. הפרומפט המלא, פרומפטי השיפור ורשימת הבדיקות נמצאים ב-[`app/build-prompt.md`](../app/build-prompt.md).

## שני מסלולי חיבור, ולמה בחרנו באחד

אפליקציה כזו יכולה לקבל נתונים בשתי דרכים:

| | מסלול א': ישירות מ-Airtable | מסלול ב': דרך webhook של n8n (WF13) |
|---|---|---|
| איך | האפליקציה קוראת ל-Airtable API עם אסימון גישה (PAT - Personal Access Token), דרך אינטגרציה מובנית או פונקציית שרת | האפליקציה שולחת בקשת POST אחת לנקודת קצה ב-n8n, ו-n8n ניגש ל-Airtable ולסוכן |
| מפתחות באפליקציה | אסימון Airtable עם הרשאות לכל הבסיס | מפתח אחד שמאפשר רק את הפעולות ש-WF13 חושף |
| איפה נאכפים הכללים | מפוזר: חלק באפליקציה, חלק בתהליכים | במקום אחד: WF13 |
| צ'אט עם הסוכן | דורש בכל מקרה קריאה ל-n8n | אותה נקודת קצה |
| מעבר בין פלטפורמות | כל פלטפורמה מתחברת אחרת | החוזה זהה ב-Lovable וב-Base44 |

**ההחלטה: רק מסלול ב'.** הסיבות:

1. **משטח חשיפה קטן.** אסימון Airtable מאפשר לקרוא, לשנות ולמחוק כל רשומה בבסיס. המפתח של WF13 מאפשר רק `list` לארבע טבלאות (שש, אחרי הפעלת לקוחות והזמנות), `create` לשלוש מהן, ו-`chat`. אין מחיקה ואין עדכון מהאפליקציה.
2. **כלל אחד, מקום אחד.** הטבלאות המותרות, הערכים ההתחלתיים והשגיאות מוגדרים ב-WF13. אם משנים כלל, משנים אותו פעם אחת.
3. **ניידות.** הממשק תלוי בפלטפורמה, אבל החוזה של WF13 לא. אם עוברים מ-Lovable ל-Base44, רק הממשק נבנה מחדש.
4. **עקביות עם האוטומציות.** חשבונית שנוצרת מהאפליקציה נכנסת ל-Airtable עם Status = New, בדיוק כמו חשבונית שהוזנה ידנית, ו-WF01 ו-WF08 ממשיכים משם.

המחיר של הבחירה: כל קריאה מהאפליקציה היא הרצה ב-n8n (חשוב לתמחור, ראו "מגבלות"), ויש קפיצה נוספת ברשת, כך שטעינה איטית מעט יותר מקריאה ישירה.

## החוזה מול WF13

כל הבקשות נשלחות ב-POST לכתובת `https://<n8n-host>/webhook/kilohertz/app` עם הכותרת `x-api-key` וגוף JSON:

| פעולה | גוף הבקשה | תשובה |
|---|---|---|
| רשימה | `{"action":"list","table":"Invoices"}` (או Leads, Products, Tasks) | `{"ok":true,"table":"...","records":[{"id":"rec...","fields":{...}}]}`, עד 100 רשומות |
| יצירה | `{"action":"create","table":"Leads","payload":{...}}` (או Invoices, Tasks) | `{"ok":true,"id":"rec..."}` |
| צ'אט | `{"action":"chat","message":"...","sessionId":"..."}` | `{"ok":true,"reply":"..."}` |
| כפילות | `create` ל-Leads עם מייל שכבר קיים | `{"ok":false,"error":"..."}` עם HTTP 409, בלי יצירת רשומה |
| שגיאה | פעולה לא מוכרת או טבלה לא מותרת | `{"ok":false,"error":"..."}` עם HTTP 400 |

שמות השדות ב-`payload` זהים לשמות ב-[`data/schema.json`](../data/schema.json). תאריכים נשלחים בפורמט ISO (`YYYY-MM-DD`) ומוצגים בממשק כ-dd/mm/yyyy.

## מודל האבטחה

```
דפדפן (נועה, מחוברת)  →  פונקציית שרת באפליקציה  →  WF13 ב-n8n  →  Airtable / OpenAI
      בלי סודות             מחזיקה URL + x-api-key      Header Auth       Credentials של n8n
```

1. **התחברות לאפליקציה.** האפליקציה פרטית, עם משתמש אחד. בקשה בלי התחברות לא מגיעה לפונקציית השרת.
2. **פונקציית שרת אחת** (`kilohertz-api`): Edge Function ב-Lovable או Backend Function ב-Base44. רק היא מכירה את כתובת ה-webhook ואת המפתח, שנשמרים כסודות של הפלטפורמה (`N8N_APP_WEBHOOK_URL`, `N8N_APP_API_KEY`).
3. **אימות ב-n8n.** צומת ה-Webhook ב-WF13 מוגדר עם Header Auth. בקשה בלי מפתח נכון נדחית לפני שהתהליך נוגע בנתונים.
4. **רשימה מותרת.** WF13 מאפשר רק את הטבלאות והפעולות שבחוזה. כל השאר מקבל שגיאה.
5. **המפתחות האמיתיים נשארים ב-n8n.** אסימון Airtable ומפתח OpenAI שמורים כ-Credentials ב-n8n ולא קיימים באפליקציה בשום צורה.
6. **בדיקה:** בלשונית Network בדפדפן לא אמורה להופיע כתובת ה-webhook ולא הכותרת `x-api-key`.

## איך בונים

### ב-Lovable

1. יוצרים פרויקט חדש ומפעילים את Lovable Cloud (נדרש לפונקציות שרת, לסודות ולהתחברות).
2. מדביקים את הפרומפט הראשי מ-`app/build-prompt.md` ומחכים לגרסה הראשונה.
3. במסך Secrets מוסיפים את `N8N_APP_WEBHOOK_URL` ואת `N8N_APP_API_KEY`.
4. מוודאים שנוצרה Edge Function בשם `kilohertz-api` ושהממשק קורא לה בלבד. אם לא, מבקשים זאת במפורש בצ'אט.
5. מפעילים התחברות במייל ויוצרים את המשתמש של נועה. מבטלים הרשמה עצמית של משתמשים חדשים.
6. מריצים את פרומפטי השיפור אחד אחד, ובודקים אחרי כל אחד.
7. מפרסמים (Publish) ועוברים על רשימת הבדיקות.

### ב-Base44

1. יוצרים אפליקציה חדשה ומדביקים את הפרומפט הראשי.
2. אם Base44 יוצר ישויות (Entities) משלו לחשבוניות, לידים וכו', מבקשים למחוק אותן: האפליקציה לא מחזיקה נתונים.
3. מפעילים Backend Functions (ייתכן שנדרשת תוכנית בתשלום) ובמסך הסודות מוסיפים את שני הערכים.
4. מוודאים שנוצרה פונקציה `kilohertz-api` שמעבירה את הבקשות ל-n8n, ושהממשק קורא רק לה.
5. בהגדרות האפליקציה מגדירים אותה כפרטית ומזמינים רק את נועה.
6. מריצים את פרומפטי השיפור, מפרסמים, ועוברים על רשימת הבדיקות.

בוחרים פלטפורמה אחת. שתיהן עומדות בדרישות; ההבדל הוא בעיקר בהעדפת עבודה ובתמחור.

## בדיקות קבלה

- [ ] הממשק בעברית, RTL, ₪ ו-dd/mm/yyyy.
- [ ] לוח הבקרה מציג ארבעה מדדים, וההכנסות תואמות לסכום ידני ב-Airtable.
- [ ] כל מסכי הטבלאות נטענים, עם חיפוש, סינון ומיון.
- [ ] מסכי לקוחות והזמנות מציגים מצב ריק כל עוד הטבלאות לא הופעלו, ונתונים אחרי הוספת הטבלאות והרחבת הרשימה ב-WF13.
- [ ] קישור המסמך נפתח בדרייב.
- [ ] יצירת ליד, חשבונית ומשימה יוצרת רשומה ב-Airtable עם הסטטוס ההתחלתי הנכון.
- [ ] ליד עם מייל שכבר קיים נדחה (409) עם הודעה ידידותית, ולא נוצרת רשומה כפולה.
- [ ] חשבונית חדשה מקבלת מע"מ, מספר וקישור תוך כמה דקות (WF01 + WF08).
- [ ] הצ'אט עונה בעברית וזוכר את ההקשר בתוך אותו סשן.
- [ ] אין סודות בתעבורת הדפדפן.
- [ ] טבלה או פעולה לא מותרת מחזירה הודעת שגיאה ידידותית.
- [ ] משתמש לא מחובר לא יכול להשתמש באפליקציה.

## מגבלות

- **משתמש אחד.** אין תפקידים, אין הרשאות לפי משתמש ואין יומן פעולות לפי משתמש. הוספת עובדים דורשת שלב נוסף.
- **עד 100 רשומות לטבלה.** הפעולה `list` מחזירה עד 100 רשומות, ולכן לוח הבקרה מחושב על המדגם הזה. בנפחים גדולים יותר צריך להוסיף ל-WF13 פעולת סיכום ייעודית.
- **מכסות Airtable.** ל-Airtable יש מגבלה של כ-5 בקשות לשנייה לבסיס. כל רענון של לוח הבקרה שולח ארבע בקשות, והן מתחלקות את המכסה עם הטריגרים של התהליכים. אין שכבת מטמון, ולכן לא כדאי לרענן אוטומטית בתדירות גבוהה.
- **עלות הרצות.** כל קריאה לאפליקציה נספרת כהרצה ב-n8n Cloud.
- **אין עדכון ומחיקה.** האפליקציה יוצרת וקוראת בלבד. תיקון רשומה נעשה ב-Airtable.
- **נעילת פלטפורמה.** ממשק שנבנה ב-Lovable לא עובר כמו שהוא ל-Base44, ולהפך. מה שנייד הוא בסיס הנתונים, החוזה של WF13 והפרומפט.
- **תלות בזמינות n8n.** אם n8n לא זמין, האפליקציה לא מציגה נתונים. אחרי הפעלה מחדש של n8n צריך להריץ שוב את WF06 ו-WF07 כדי שהצ'אט יכיר את המדיניות.
